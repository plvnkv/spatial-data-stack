# GitOps для GIS відділу на одному сервері

## Мета й межі

З чистого Ubuntu Server можна відтворювано розгорнути внутрішню GIS-платформу для працівників відділу. Працівники підключаються з робочих місць через LAN. Оператор оновлює конфігурацію через pull request у GitHub.

Цільова ОС за пропозицією — Ubuntu Server 26.04 LTS. Початковий профіль — один вузол k3s на фізичному сервері або VM, amd64 як профіль перевірки. У першій версії усі працівники можуть читати повний набір опублікованих векторних і растрових даних. GeoNode окремо керує видимістю ресурсів у порталі та правами на редагування й публікацію. Система працює з даними, дозволеними для всього відділу. Прихований у GeoNode шар може бути доступний через Martin або TiTiler. Регіональні обмеження поза порталом, публічний доступ, HA та імпорт наявного каталогу виходять за межі першої версії.

## Підходи

- **Окремі застосунки Argo CD, обрано користувачем.** Один кореневий Application підключає окремі застосунки. Оновлення тайлерів можна відокремити від порталу й сховищ. Залежності потребують власних перевірок готовності.
- **Один спільний Helm-чарт.** Менше об’єктів верхнього рівня, але оновлення будь-якого компонента проходить через спільний цикл синхронізації.

## Репозиторій і життєвий цикл

- `bootstrap/` — повторюваний скрипт для чистого Ubuntu, конфігурація k3s, встановлення Argo CD із закріпленою версією, підключення GitHub і застосування кореневого Application. Повторний запуск зберігає наявні дані та облікові записи. Root Application і правила доступу задає адміністратор.
- `clusters/single-node/` — AppProject, дочірні Applications і параметри інсталяції. DNS-імена, LAN CIDR і параметри сховища налаштовуються для конкретного майданчика.
- `charts/` — власні чарти й конфігурація зафіксованих upstream-чартів. Дочірні Applications є одиницями синхронізації, Helm рендерить маніфести для Argo CD. GeoNode і GeoServer оновлюються разом.
- `.github/workflows/` — перевірки pull request через helm lint, рендер зразка конфігурації та валідацію маніфестів для цільової версії Kubernetes. GitHub Actions не потребує доступу до LAN або kubeconfig. Argo CD сам опитує GitHub через вихідне HTTPS-з’єднання. Вихід до реєстрів образів і джерел чартів потрібен під час встановлення та оновлень.
- `docs/` — передумови, встановлення, публікація тестових даних, оновлення, резервування й відновлення.

Базова послідовність — bootstrap, сховища й ініціалізація, GIS-сервіси. Jobs для створення баз, ролей і бакетів та для міграцій мають бути повторюваними. Їхній успіх перевіряється за фактичною доступністю залежностей. Сам порядок створення Applications готовності сервісів не гарантує. Argo CD автоматично підтягує зміни з основної гілки. Автоматичне видалення ресурсів із даними вимкнене, томи зберігаються при видаленні або перевстановленні застосунку. Оновлення схеми БД має задокументований шлях відновлення з резервної копії.

## Сервіси й дані

| Застосунок | Відповідальність |
| --- | --- |
| PostGIS | Один екземпляр PostgreSQL з окремими базами для метаданих порталу та GIS-даних. Окремі облікові записи для застосунків. Martin читає GIS-дані через службову роль лише для читання. PostGIS має внутрішній ClusterIP. Мережевий доступ до бази обмежений авторизованими компонентами платформи. Працівники працюють із даними через GIS-сервіси. |
| RustFS | Внутрішній S3 endpoint, standalone і постійний том. Окремі облікові дані на запис COG і на читання для TiTiler. Бакет з COG залишається приватним. |
| GeoNode та GeoServer | Узгоджена пара образів із потрібною конфігурацією OAuth2 і GeoFence. Включає компоненти фонового виконання, потрібні обраному релізу GeoNode. Метадані зберігаються в PostgreSQL, файли порталу й конфігурація GeoServer — на постійних томах. |
| Martin | Векторні тайли з дозволених для публікації джерел у PostGIS. Каталог джерел задає оператор. База метаданих GeoNode відокремлена від цього доступу. |
| TiTiler | Растрові тайли з COG у RustFS. LAN endpoint приймає ідентифікатор растра і на сервері визначає S3-ключ у дозволеному бакеті. У користувача немає можливості передати довільний URL або шлях. |

Векторний потік для перевірки — записати зразок у PostGIS, опублікувати в GeoNode через GeoServer і отримати тайл через Martin. Растровий потік — покласти COG у RustFS та отримати тайл через TiTiler. Растрові ресурси порталу публікуються окремим потоком GeoNode. Спільний доступ до растрів через TiTiler охоплює перегляд тайлів. Окремий LAN endpoint для завантаження оригіналів COG виходить за межі першої версії. Автоматичне перенесення кожного завантаження GeoNode в каталоги Martin і TiTiler не входить у першу версію.

## Мережа, секрети й зберігання

- Пропоновані налаштування — вбудований Traefik у k3s, внутрішній DNS, TLS-сертифікати від довіреного у відділі CA. Інструкція включає довіру до CA на робочих місцях. Доступ до Kubernetes API, SSH і Argo CD обмежений адміністраторами. RustFS і службові endpoints доступні всередині кластера. Хостові правила доступу перевіряються з дозволеної та сторонньої мереж.
- Початкові секрети й read-only облікові дані GitHub створює bootstrap із захищених вхідних даних оператора. Git містить посилання на Kubernetes Secrets, а оператор зберігає матеріал для відновлення в окремому захищеному сховищі. Секрети не потрапляють у логи CI чи Git.
- Постійні томи використовують налаштовану директорію на диску даних і політику Retain. Втрата вузла зупиняє платформу. Резервні копії мають виходити за межі цього вузла. Для першої версії репозиторій надає інструкцію й команди для узгодженої копії БД, об’єктів RustFS, файлів GeoNode, каталогу GeoServer і матеріалу bootstrap. Для копії оператор призупиняє записи, щоб відновити дані за один контрольний момент. Окремо документується відновлення SQLite k3s разом із серверним токеном, якщо відновлюється сам кластер.
- Оператор задає доступну ємність диска, DNS, CA, мережеві діапазони та зовнішню ціль резервування. Ці значення не потрібні для написання шаблонів і мають бути задані перед розгортанням на робочому сервері.

## Припущення для погодження

- Сервер має вихідний HTTPS до GitHub, реєстрів образів і джерел чартів. Для ізольованої мережі потрібна інша схема доставки.
- Спільний растровий доступ у першій версії означає перегляд через TiTiler. Оригінали COG залишаються у внутрішньому RustFS.

## Перевірка готовності

1. На чистій Ubuntu VM bootstrap проходить двічі, всі дочірні застосунки сходяться до Healthy та Synced. Після перезавантаження дані й конфігурація зберігаються.
2. Із LAN відкриваються HTTPS endpoints, а SQL-порт PostGIS та інші службові порти й інтерфейси недоступні зі звичайного робочого місця. Martin читає GIS-дані своєю службовою роллю, а спробу запису від цієї ролі відхилено.
3. Тестовий вектор віддається через Martin, тестовий COG віддається через TiTiler, а довільний URL не приймається. Обидва типи даних перевірено після перезапуску.
4. Два користувачі GeoNode мають різні права на тестовий ресурс. Обмеження порталу й GeoServer перевіряються окремо від спільного доступу через Martin і TiTiler.
5. Резервну копію тестового набору можна відновити на чистому вузлі, після чого повторно проходять обидва потоки публікації.

## Рішення для плану реалізації

Підібрати та зафіксувати сумісні версії образів і чартів, узяти upstream-чарт RustFS за умови проходження перевірок standalone та S3, визначити точні шаблони Jobs і readiness probes, задокументувати параметри ресурсів і перевірити розгортання на Ubuntu VM. Робоче розгортання залежить від проходження цих перевірок та отримання параметрів майданчика.
